# agent-works

两个能跑起来的 Agent 项目，配上能复现的评测脚本。

- **项目一** 文献问答 RAG：切分 → 检索 → 组装上下文 → 生成 → 挂引用
- **项目二** 多工具任务助手：LangGraph 编排的工具调用与异常处置

两边的数字都是脚本跑出来的，不是手写的。`git clone` 之后装个依赖就能重跑。

## 快速开始

```bash
pip install -r requirements.txt

bash run_all_evals.sh        # Linux / macOS / Git Bash
.\run_all_evals.ps1          # Windows PowerShell
```

单独跑某一步：

```bash
python lit-qa-agent/litqa/test_agent.py          # 自检 7 项
python lit-qa-agent/eval/evaluate.py             # 评测
python task-assistant/taskgraph/test_graph.py    # 自检 11 项
python task-assistant/eval/evaluate.py           # 评测
```

`task-assistant/taskgraph/service.py` 提供 FastAPI 接口，需要额外装
`fastapi` 与 `uvicorn`；不装不影响自检和评测。

## CI 里跑什么

`.github/workflows/ci.yml` 在每次 push 时执行：Python 3.10 与 3.12 各跑一遍
自检 + 评测，然后对四个关键指标做硬断言（见下文「指标门禁」）。评测报告
作为 artifact 上传，网页上能直接点开。

## 项目一 · 文献问答 RAG

语料 12 篇合成文献，问题集 150 条（含资料外提问）。三组切分参数对照：

| 配置 | chunk | overlap | top_k | 引用正确率 | 覆盖率 | 拒答率 | 幻觉率 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| baseline-512 | 512 | 0 | 3 | 82.5% | 77.1% | 100% | 0% |
| tuned-320 | 320 | 64 | 4 | 88.4% | 84.7% | 100% | 0% |
| tuned-256 | 256 | 80 | 5 | **93.1%** | **91.0%** | 100% | 0% |

切分粒度越小、top_k 越大，引用正确率越高，但检索开销和延迟同步上升。
256/80/top_k=5 是准确率与成本的折中点，不是刷出来的最优解。

同一套切分参数再跑一遍 LangChain + FAISS 的对照：

| 配置 | 切分 | 检索 | 引用正确率 | 覆盖率 | 综合 |
| --- | --- | --- | --- | --- | --- |
| tuned-320 | 自研 | BM25 | 88.4% | 84.7% | 85.3% |
| lc-vector-320 | LangChain | FAISS | 47.6% | 31.2% | 34.0% |

向量检索在这个语料上明显更差，我保留了这条负面结果而没有调参掩盖它。
原因不难猜：`VectorRetriever` 用的是字符 2~3 gram 的 TF-IDF 向量，
对中文术语的重合度远不如 BM25 的分词 + IDF 直接。这一栏演示的是向量检索的
工程流程（建索引、metadata 携带、分数归一化），不是它的检索效果。换真实
embedding 模型后才谈得上比较——`VectorRetriever` 里换掉 `_TfidfCharEmbeddings`
即可，其余逻辑不用动。

拒答率 100%、幻觉率 0% 的原因见下面「拒答为什么要两道闸门」。

## 项目二 · 多工具任务助手

用例集 29 条（正常 8 / 异常 21），同一份故障序列下对照两种处置策略：

| 指标 | baseline | enhanced |
| --- | --- | --- |
| 工具调用成功率 | 44.4% | **94.4%** |
| 异常处置率 | 100% | 100% |
| 升级人工比例 | 0% | 33.3% |
| 平均重试次数 | 0 | 0.72 |
| 平均耗时 | 10.9ms | 17.8ms |
| 崩溃次数 | 0 | 0 |

baseline 只调用一次、失败就返回错误，这是多数 Agent 的默认写法；enhanced
多了参数校验、分类重试和降级换路。差值 0.5 完全来自处置策略——故障序列
由确定性的注入器生成，两组跑的是同一串故障。

升级人工 33.3% 不是凑出来的数字：冲突用例只有 3 条，其中 1 条真的检索到了
互相矛盾的数据，另外 2 条检索本身正确且一致，对它们升级属于误报。

## 几个我觉得值得说的设计

### 引用锚点用位置，不用内容哈希

```python
@property
def cite_ref(self) -> str:
    return f"{self.doc_id}#p{self.page}#c{self.chunk_index}"
```

文献改版后内容哈希会全变，历史引用就追不回来了。位置标识在同一版本文档内
始终稳定——史料溯源场景里这是硬需求。

### 拒答要两道闸门

只看 BM25 分数不够，「本文」「多少」这类虚词会把不相关文档的分数抬上去，
模型就会拿着不相干的段落硬编。第二道闸门看问题实词在检索结果里的覆盖率，
两道都过才放行。

分数阈值按检索器分别标定：BM25 是加权和（1~10 量级），向量检索是归一化
余弦（0~1），共用一个阈值必然一边全拒答、一边永不拒答。

领域外术语（ImageNet、BLEU 等）走单独的标记词短路，纯词面覆盖率对这类
幻觉没辙。局限写在 `litqa/agent.py` 的注释里。

### 工具失败必须分类

笼统的「重试一下」是错的，除零重试一万次还是除零：

| 异常类型 | 处置 | 理由 |
| --- | --- | --- |
| 瞬时超时 | 退避重试 | 重试有意义 |
| 参数缺失 | 直接返回交上层 | 同样参数必然同样失败 |
| 检索为空 | 降级为「无结果」 | 流程能继续，不该中断 |
| 结果冲突 | 升级人工 | 自动裁决的风险大于收益 |
| 确定性错误 | 明确报错 | 无效重试是纯浪费 |

### 计算器绝不 eval 原始字符串

工具入参直接 `eval()` 等于开了个远程代码执行口子——模型幻觉或 prompt 注入
都可能传出 `__import__('os').system(...)`。这里用 AST 白名单求值，并限制
指数上限。`test_graph.py` 里有针对 `__import__`、`__class__` 等攻击模式的测试。

### LangGraph 用了什么

项目二的编排是真的 `StateGraph`：plan / act / finish / escalate 四个节点，
`_route` 决定下一跳，步数上限用框架原生的 `recursion_limit`。

`graph_handrolled.py` 里留了一份不用框架的等价实现，跑同一份评测集。
`test_handrolled_and_langgraph_agree` 会断言两者行为一致——保留它是为了
回答「框架到底省了什么」，也为了在换框架改出差异时能立刻发现。

## 我知道的局限

1. **向量检索没赢。** 上面说了，用的是字符 n-gram TF-IDF，换成真 embedding
   才算公平比较。
2. **规划器是规则式的**，不是 LLM 驱动。好处是可复现可审计，代价是复杂任务
   的拆解能力有限。
3. **领域外标记词是人工词表**，换 embedding 后应替换为向量距离阈值。
4. **网页搜索用静态语料模拟**，不访问真实网络。评测离线可复现是刻意取舍。
5. **语料是合成的**，不是真实史料。事实密度和真实文献有差距，评测结果不能
   直接外推到真实数据上。

## 接真实大模型

```bash
export AGENT_LLM_BACKEND=online
export AGENT_LLM_API_KEY="sk-..."
export AGENT_LLM_BASE_URL="https://api.openai.com/v1"   # 可选
export AGENT_LLM_MODEL="gpt-4o-mini"                    # 可选
python lit-qa-agent/eval/evaluate.py
```

默认的离线后端是个**基线**而不是摆设：任何检索增强系统都不该弱于「把最相关
的几段原文直接拼出来」。接上真实模型之后的提升才有参考价值。
